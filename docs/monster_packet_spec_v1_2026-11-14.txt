# 몬스터 패킷 전달 명세 v1

작성일: 2026-11-14 / B 담당 유정선
상태: B 측 개발 기준 전달안. A 이용재·C 이채민 확인 대기.
기준: SUN 9d17944의 network.h, monster.h, monster.cpp, renderer.cpp 및 A 네트워크 문서(YONG 64d8902).
YONG 최신 코드 대조, 브랜치 통합 및 송수신 구현은 아직 수행하지 않았다.

## 1. 기존 형식 유지

11/14 구현: 기존 MonsterEntry 구조체의 이름을 MonsterStateData로 정리하고 using MonsterEntry = MonsterStateData 별칭으로 기존 참조를 유지한다. 기존 번호, 필드 순서, 타입, pack(1), 전송 바이트 형식은 유지한다. MonsterStateData는 함수가 아니라 한 개체의 전송 상태 구조체이다.

| 구조체 | 확인한 크기 |
|---|---:|
| PacketHeader | 4바이트 |
| MonsterStateHeader | 2바이트 |
| MonsterEntry | 17바이트 |
| BossStateData | 43바이트 |
| MonsterHitData | 3바이트 |
| PlayerStateData | 23바이트 |

위 크기는 11/14 로컬 헤더를 포함한 C++ sizeof 프로그램 실행으로 확인하였다. 양쪽 브랜치 통합 시 동일한지 다시 확인한다.

## 2. 전송 규칙

- 호스트 업데이트 후 5게임 프레임마다 종류별 완전 스냅샷을 보낸다. 15ms 타이머 기준 명목상 75ms이며 실제 시간 간격을 보장하지 않는다.
- PKT_MONSTER_STATE(5): PacketHeader + MonsterStateHeader + MonsterEntry[count].
- kind 0~4를 각각 전송하며, 개체가 없어도 count=0으로 전송한다.
- PKT_BOSS_STATE(12): PacketHeader + BossStateData. 보스가 없을 때도 비활성 상태를 전송한다.
- PKT_MONSTER_HIT(11): PacketHeader + MonsterHitData. 클라이언트의 공격 요청이며 호스트 자신의 공격도 같은 검증 경로를 사용한다.
- 상태 송신자의 playerId는 0. 실제 호스트 연결인지 확인해야 하며 헤더 ID만 신뢰하지 않는다.

## 3. 길이·슬롯 검증

- count는 종류별 0~100, slot은 0~99.
- 몬스터 패킷 크기는 6 + 17 * count. 최대 1,706바이트, 빈 패킷 6바이트.
- 보스 상태 47바이트, 타격 요청 7바이트.
- 실제 패킷 길이, hdr.size, 기대 크기가 모두 일치해야 한다.
- 기존 수신 상한 4,096바이트를 유지한다. 상수화는 A 통합 시 별도 수정 사항으로 기록한다.
- 잘못된 종류·길이·중복 슬롯·범위 밖 값은 전체 적용 전에 거부한다. 잘못된 패킷 때문에 기존 상태를 일부만 변경하지 않는다.
- 누락된 슬롯은 기본 상태로 초기화하여 기존 active/isAlive/isDead가 남지 않게 한다.
- count는 개체 수이지 배열 순회 상한이 아니다. slot 2와 9를 보내면 count=2지만 순회 상한은 10이다.
- 수신 후 해당 종류의 순회 상한은 최대 유효 slot + 1, 빈 패킷은 0으로 설정한다. 기존 배열 전체 순회는 비활성 상태로 필터링한다.

## 4. 종류별 배열 및 전송 대상

| kind | 실제 저장 대상 | 포함 조건 |
|---|---|---|
| 0 MON_NORMAL | monsters[slot] | active=true; 사망 애니메이션 포함 가능 |
| 1 MON_TURTLE | turtles[slot] | isAlive=true |
| 2 MON_BROWN_TURTLE | 예약 | 현재 count=0 |
| 3 MON_ANGEL_TURTLE | angelTurtles[slot] | isAlive=true |
| 4 MON_FIREBALL | fireballs[slot] | active=true |
| 5 MON_BOSS | bowser | 타격 요청에서만 slot=0, 상태는 별도 패킷 |

- stage 3의 갈색 거북이도 현재 turtles 배열에 저장되고 렌더러가 스테이지별 이미지를 고른다. kind 1과 2로 중복 전송하지 않는다.
- 천사 거북이는 현재 초기화에서 active가 설정되지 않으므로 active만 기준으로 하면 누락된다.
- 선택 조건과 상태 플래그는 별개다. 포함된 Entity의 플래그는 그대로 전달한다.

## 5. 필드 의미

- x/y: 월드 좌표. 화면 좌표는 렌더링 시 worldX - cameraX.
- vx/vy: 기존 게임 프레임 기준 속도.
- width/height: 기존 충돌 크기. 이미지 크기로 바꾸지 않는다.
- 거북이 state: NORMAL=0, SHELL=1, SPINNING=2.
- 천사 거북이 state: FLYING=0, HIDE=1.
- 일반 몬스터·불꽃의 미사용 state는 0.
- Entity의 isAlive/isDead/active/isFalling은 각각 대응 비트로 전달.
- 거북이 damage 및 direction은 DAMAGE/FACING_LEFT, 천사 거북이 goingUp은 GOING_UP 비트 사용.
- 불꽃은 ACTIVE, 위치·속도·크기·motion만 사용하고 미사용 값은 0.
- 필드 축소 변환 전에 표현 범위를 검사한다. 정상적인 공중·화면 밖 위치를 맵 내부로 강제 제한하지 않는다.

## 6. 타이머 의미 및 이전 설명 정정

이전 검토의 '거북이는 기존 카운터'라는 설명을 정정한다. 실제 shellTimer와 damageTimer는 GetTickCount()로 저장한 시작 시각이다. 이를 uint16_t로 그대로 전송하면 값이 잘리고 PC별 가동 시각도 달라진다.

| 종류 | timerA | timerB |
|---|---|---|
| 일반 몬스터 | 사망 표시 경과 ms | 0 |
| 거북이 | SHELL 상태 경과 ms | SPINNING이며 damage=false일 때 피해 활성화 대기 경과 ms |
| 천사 거북이 | HIDE 진입 경과 ms | 0 |
| 불꽃 | 기존 motion 인덱스 | 0 |

- 비해당 상태의 타이머는 0.
- unsigned 시각 차이로 경과 시간을 계산하고 65,535에 포화시킨다. 단순 축소 변환으로 순환시키지 않는다.
- 클라이언트는 타이머만으로 AI 상태 전환이나 사망·부활을 판정하지 않는다.
- 표시 코드가 시작 시각을 요구하면 localNow - elapsed로 복원한다. 미시작과 경과 0은 상태 플래그로 구분한다.
- 일반 몬스터의 deadStart 설정과 active 해제는 호스트 업데이트로 옮기는 것이 후속 구현 요건이다. 멀티 클라이언트 렌더러는 권위 상태를 바꾸지 않는다. 싱글 표시 시간은 유지한다.
- BossStateData의 fireTimer/fireDuration/fireInterval/jumpTimer/jumpInterval은 현재 프레임 카운터·기간이므로 프레임 단위를 유지한다.
- 보스의 로컬 렌더 애니메이션과 수신 frame 필드의 연결은 C와 조율한다.

## 7. 판정 및 싱글 호환

- 싱글은 기존 로컬 계산·판정 유지.
- 멀티 호스트만 몬스터 AI·피해·제거·상태 전환을 확정.
- 클라이언트는 수신 상태를 적용하되 자기 캐릭터와의 충돌 검사는 수행.
- 자기 캐릭터 피격·사망과 밟은 후 반동은 각자 판정. 공용 목숨 차감은 호스트에서 중복 방지.
- 몬스터 피해 요청은 종류·슬롯·타격 방식·현재 상태를 검증하고 기존 게임의 허용 규칙을 유지한다. 보스 밟기 불가 등 예외를 유지한다.
- 현재 타격 패킷에는 공격 식별자가 없다. 반복 타격 가능한 대상의 동일 공격 중복 방지는 후속 구현에서 재사용 대기시간·공격 상태 검증으로 정하고, 부족하면 별도 명세 변경이 필요하다. 모든 중복 공격 방지가 해결된 것은 아니다.

## 8. 스테이지 전환

패킷에 stage 필드가 없으므로 기존 EVT_STAGE_LOAD와 같은 TCP 스트림의 순서를 활용한다.
호스트는 이전 스냅샷 송신 중단 → 전환 이벤트 → 새 스냅샷 순서로 보낸다.
클라이언트는 메인 스레드에서 같은 순서로 초기화·적용한다.
비동기 로드나 다른 전송 경로가 도입되면 stage/epoch 필드 추가를 검토해야 한다.

## 9. 역할과 확인 요청

- A: 송수신·큐·송신자 구분·연결 종료, 최신 YONG 헤더 대조.
- B: 호스트 AI/타격 분리, 직렬화·수신 적용, 검증·슬롯 정리, 스테이지 전환 연결.
- C: 좌표·사망 상태 렌더링, 렌더러의 권위 상태 변경 제거를 B와 조율.
- A 접속 구현 예정(~11/21)과 B 통합 테스트(11/20~21)의 준비 시점 확인 필요.
- 제공된 원본 일정 이미지의 11/13은 필드 초안, 11/14는 A·C와 필드 확정이다. 사용자의 추가 구현 요청에 따라 패킷 생성·해석 함수를 선행 구현했다. 실제 송수신·게임 상태 적용은 미연결이다.
